🌿 Analogy §1 The Cube Problem • Card 1 of 4
🧊
Pre-Calculating Every Possible Summary

Imagine you have a giant spreadsheet of sales data with columns for City, Product, Month, and Salesperson. Your boss wants totals "by city", "by product", "by city+product", "by all three", and every other combination — before any question is even asked.

With 4 dimensions, there are 2⁴ = 16 different ways to group the data (each dimension is either "grouped" or "totalled away"). With 10 dimensions that's 2¹⁰ = 1,024 combinations. With 20 dimensions: over a million!

We need smart algorithms that don't naively compute all of them.

📐 Formula: A cube with n dimensions has exactly 2ⁿ cuboids (sub-aggregations). Each dimension is either "kept" or "collapsed".
💡 Why it matters: Without clever algorithms, even a 15-dimension cube would require computing 32,768 separate aggregation tables. We need smarter approaches — BUC, MultiWay, Star-Cubing.
📘 Concept §1 The Cube Problem • Card 2 of 4
🗂️
Three Types of Data Cubes

Instead of always computing everything, we have three strategies:

🟦 Full Cube
Compute all 2ⁿ cuboids. Nothing is skipped. Uses the most memory, but answers any query instantly.
🟩 Iceberg Cube
Only compute cells where count ≥ min_support. Skips sparse/empty cells. Like seeing only the tip of the iceberg — the dense, meaningful data.
🟨 Shell Cube
Only pre-compute small-dimensional cuboids (e.g., 1-D, 2-D, 3-D combos). High-dimensional queries are answered on the fly by combining shells.
💡 Real use: E-commerce sites use iceberg cubes — most product × region × day combinations have zero sales. Why waste memory on them?

🌿 Analogy §2 BUC Algorithm • Card 1 of 7
🔺
BUC: Bottom-Up Cube Computation

BUC sounds like it builds from the bottom up — but there's a twist! In BUC, "bottom" refers to the lattice, not a physical pyramid.

The lattice is a graph of all cuboids. At the TOP is the most summarized (fewest dimensions = 0-D, the "all" total). At the BOTTOM is the least aggregated (all dimensions = raw data level).

BUC starts at the TOP of the lattice (the apex — the grand total) and works downward toward more detailed cuboids — hence "bottom-up" in the sense it moves toward the bottom of the lattice.

🗺️ Lattice for 3 dimensions A, B, C:
{} (0-D, apex)
A    B    C
AB   AC   BC
ABC (3-D, base)
💡 Key: The lattice has 2³ = 8 nodes for 3 dimensions. BUC visits them in a specific top-down order to enable pruning.
📘 Key Concept §2 BUC Algorithm • Card 2 of 7
✂️
Apriori Pruning — The Magic Behind BUC

This is the core insight that makes BUC fast:

If a cell's count < min_support,
ALL its more-detailed descendants
will ALSO be below min_support.

Why? When you "drill down" (add more dimensions), you split a group into smaller sub-groups. Sub-groups can only have equal or fewer members than the parent. So if the parent fails the threshold, so will all children.

Example: If "City=London" has count=3 (below threshold=5), then "City=London, Product=TV" will have count ≤ 3. Prune that entire branch!

💡 This is the Apriori anti-monotone property — the same principle used in frequent itemset mining. If a set is infrequent, all its supersets are infrequent too.

📘 Concept §2 BUC Algorithm • Card 4 of 7
📊
Dimension Ordering Matters

BUC doesn't just prune — it also cares about the order in which dimensions are processed. The right order = way more pruning.

Rule: Order dimensions by cardinality (number of unique values) — highest cardinality first.

Why high-cardinality first?
✅ Good Order
CustomerID (10,000 values) → City (50) → Category (5)
High cardinality = many small groups = more likely to fall below threshold = more pruning
❌ Bad Order
Category (5) → City (50) → CustomerID (10,000)
Low cardinality first = few big groups = rarely pruned = slow
💡 Analogy: Like filtering a job applicant pool — first filter by hardest requirement (PhD required), then by easier ones. Most pruning happens early.
📘 Concept §2 BUC Algorithm • Card 5 of 7
🗑️
Hash Partitioning Optimization

Without optimization, BUC would scan the entire database for every cuboid it computes. That's very slow.

Hash Partitioning solves this. When processing dimension A, BUC partitions the data into groups by A's values using a hash function. Each partition only contains rows relevant to that sub-group.

When BUC recurses to compute AB (fixing a value of A), it only needs to scan the A-partition — not the whole database. Subsequent dimensions sub-partition further.

💡 Benefit: Work for each partition is proportional to its size. Scan the whole DB just once per level, not once per cuboid.
⚠️ Gotcha + Flip §2 BUC Algorithm • Card 6 of 7
🚫
Can BUC Handle AVERAGE-Based Iceberg Cubes?

This is a classic exam trap. Think carefully before flipping!

🤔
Can BUC be used for AVERAGE-based iceberg cubes?
(e.g., "only keep cells where average_sales ≥ 1000")
Click to reveal answer
❌ No!
AVERAGE is NOT anti-monotonic. A parent group might have a low average, but a child sub-group could have a high average. BUC cannot safely prune children when the parent fails the average threshold. BUC's pruning only works for COUNT (and other anti-monotonic measures).
Example: "All products" avg = $50 (below threshold $100). But "Luxury products" sub-group avg = $2000! BUC would wrongly prune Luxury products.
💡 Alternative: For non-anti-monotonic measures like AVERAGE, use the H-Cubing algorithm (see Appendix) which works via top-k constraints.
📈 Performance §2 BUC Algorithm • Card 7 of 7
🏎️
BUC vs Full Cube Performance

In sparse datasets with a minimum support threshold, BUC can be orders of magnitude faster than computing the full cube.

Full Cube
• Computes all 2ⁿ cuboids
• Lots of empty cells wasted
• Memory: O(Vⁿ) where V = avg values per dim
• Good for: Dense data, ad-hoc queries
BUC Iceberg
• Prunes sparse branches early
• Only computes meaningful cells
• Memory: much smaller (just significant cells)
• Good for: Sparse data, min_support threshold
Research finding: For real-world market-basket data (~0.1% density), BUC with min_support=3 can reduce computation by 99%+ compared to full cube.
💡 Bottom line: BUC is the algorithm of choice for sparse, high-dimensional OLAP cubes with count-based thresholds.
🌿 Analogy §3 MultiWay Aggregation • Card 1 of 5
🗳️
MultiWay: Tally Everything in One Sweep

Imagine counting votes in an election. You need totals by age group, by region, by political party, AND by combinations.

You could make separate passes through all ballots for each breakdown. But that's wasteful — you'd read every ballot many times.

Instead, MultiWay reads each ballot ONCE and updates all tallies simultaneously. It's like having many tally sheets on the table and checking every sheet with every ballot.

This is the MultiWay Array Aggregation approach — compute multiple cuboids simultaneously in a single sweep of the data.

Key difference from BUC: BUC is top-down in the lattice. MultiWay sweeps through the data linearly, updating multiple cuboids at once. It's better suited for dense data.
💡 Use case: MultiWay is best when data is stored as arrays (MOLAP systems) and most cells are non-empty.
📘 Concept §3 MultiWay Aggregation • Card 2 of 5
🔢
MultiWay: MOLAP Array Approach

MultiWay works on MOLAP (Multidimensional OLAP) systems where data is stored as multi-dimensional arrays.

The key idea: sweep through the array once and compute multiple cuboids simultaneously rather than making multiple independent passes.

Step 1: Lay out a 3-D array with dimensions A, B, C
Step 2: Divide the array into chunks that fit in memory
Step 3: Process chunk by chunk, maintaining running sums for ALL 2D faces (AB, AC, BC) simultaneously
Step 4: After all chunks are done, all cuboids are computed!
💡 Benefit: Reading data from disk once (instead of 2ⁿ times) dramatically reduces I/O. The bottleneck in large datasets is usually disk reads.

💡 Concept §3 MultiWay Aggregation • Card 4 of 5
🧩
Why Chunking Matters

A large 3-D array can be millions of cells. It won't fit in RAM. Chunking divides it into small n-dimensional sub-arrays that DO fit in memory.

The Row-Major Problem: In row-major storage (like C/Python), reading column-by-column is slow (cache misses). In column-major (Fortran), reading row-by-row is slow. With a cube, you need to sweep in ALL directions — a nightmare for either storage order.

The Fix: Chunks are small enough that any element within a chunk is close to any other element on disk. Chunk access pattern is symmetric — no preferred direction.

Choosing chunk size: Balance between:
• Too small → too many chunks, overhead per chunk is high
• Too large → chunk doesn't fit in memory, defeats the purpose
• Just right → chunk fits in available memory, typically a few MB
💡 Modern CPUs: Cache lines are 64 bytes. Chunks aligned to cache sizes maximize CPU efficiency — same idea, different scale.

🌿 Analogy §4 Star-Cubing • Card 1 of 4
⭐
Star-Cubing: Best of Both Worlds

Star-Cubing is like a hybrid car — it combines the top-down efficiency of MultiWay with the bottom-up pruning power of BUC.

It also adds a clever pre-processing trick: before doing any multi-dimensional computation, it scans each dimension individually. Any value that appears very rarely gets marked with a star (*).

Think of it like a Hollywood award ceremony. Before announcing pairs or groups, they first identify which individuals are "not even nominated" (below min_support). Those people are replaced with a generic * placeholder, and all their combinations are automatically skipped.

Example: If "City=Timbuktu" has only 2 sales (below min_support=5), it gets marked as * everywhere. Any cuboid involving "City=Timbuktu" is instantly pruned.
💡 Impact: In high-dimensional sparse data, star-conversion can eliminate 70–90% of values before multi-dimensional processing even begins.

When computing related cuboids like AB and ABC, they share the A and B dimensions. Star-Cubing computes them together, sharing the work.

⭐ Star Nodes §4 Star-Cubing • Card 3 of 4
✨
Star Nodes: Early Pruning

Before Star-Cubing begins multi-dimensional work, it scans each dimension independently and identifies infrequent values (count < min_support).

These values are replaced with a star node (*). All these * values are then grouped together, and their cuboids are ignored.

Example with min_support = 3:
Original City values:
NYC: count = 150 ✅
LA: count = 89 ✅
Boise: count = 2 ⭐→*
Midway: count = 1 ⭐→*
After star conversion:
NYC: 150 ✅
LA: 89 ✅
*: {Boise, Midway} grouped
NYC×* and LA×* cuboids = pruned
💡 Why it works: If City=Boise has count < min_support alone, then City=Boise ∩ anything_else will also have count < min_support. Star node prunes all its combinations at once.

❓
How does Star-Cubing prune the search space early?

🌿 Analogy §5 Shell Fragments • Card 1 of 3
🐚
Shell Fragments: Pre-compute Small Combos

Imagine you're a travel agent with 50 destination attributes (country, climate, price range, etc.). A customer can ask about ANY combination. Pre-computing every pair would be 50×49÷2 = 1,225 pairs. Every triple = 19,600 combos. That's too many!

Instead, you pre-compute only combos of up to 3 attributes — your "shell fragments." When a complex query arrives combining 5 attributes, you grab the right 3-D fragments and combine them quickly on the fly.

Shell Fragments do exactly this for ultra-high-dimensional data.

The math: With 50 dims, computing ALL 2-D cuboids = 1,225 tables. With shell fragments of size F=3: C(50,3) = 19,600 small fragments. But each fragment is tiny and can answer most OLAP queries when combined.
💡 Use case: Genomics data with 100,000+ gene dimensions. Shell Fragments make OLAP queries feasible where full or iceberg cubes are impossible.
📘 Algorithm §5 Shell Fragments • Card 2 of 3
🔬
Shell Fragment Algorithm

The Shell Fragment approach works in two phases:

Phase 1: Pre-computation (offline)
For each group of F dimensions (F ≤ 3 typically):
• Build a small local cube (the "shell fragment")
• Store inverted TID lists for each cell value
• A TID list = set of transaction IDs with that value
Phase 2: Query Answering (online)
When a query arrives (e.g., Age=25, City=NYC, Product=TV):
• Look up TID list for Age=25: {1, 4, 7, 12}
• Look up TID list for City=NYC: {1, 3, 7, 9, 12}
• Intersect: {1, 7, 12} ← matching transactions
• Count = 3
💡 Speed: TID list intersection is extremely fast using bitset operations. Modern CPUs can intersect millions of IDs per second.

What is a TID List?
❓
What is a TID list in Shell Fragments, and why is intersecting them useful?
Click to reveal
✅
A TID list is a list of Transaction IDs that contain a particular dimension value. Intersecting TID lists from multiple dimensions gives the exact set of transactions matching ALL conditions simultaneously — very fast! Instead of scanning all records, we just intersect small ID lists.
Quick Example:
TID(Gender=F) = {2, 5, 6, 9, 11}
TID(City=Boston) = {1, 5, 9, 13}
TID(Product=Laptop) = {5, 8, 9, 15}
∩ = {5, 9} → Only 2 female Bostonians bought a laptop

📚 Appendix First Principles & Math
🔬
Mathematical Foundations
📐 Full Cube vs Iceberg Cube — Formal Definition

Let D = {d₁, d₂, ..., dₙ} be a set of n dimensions. A full data cube computes all 2ⁿ cuboids, where each cuboid is a GROUP BY aggregation on a subset S ⊆ D.

An iceberg cube computes only cuboid cells c where: measure(c) ≥ min_support

For COUNT: count(c) ≥ θ where θ is the minimum threshold.

Formally: Iceberg_Cube = { c ∈ Full_Cube | count(c) ≥ θ }

📐 Apriori Anti-Monotone Property — Formal Statement

A measure f is anti-monotone with respect to a cuboid lattice if and only if:

∀ cuboids c₁, c₂: c₁ is an ancestor of c₂ ⟹ f(c₁) ≥ f(c₂)

Translation: Going from a less-detailed to a more-detailed cuboid (drilling down) can only decrease or maintain the aggregate value, never increase it.

Anti-monotone measures: COUNT, SUM (for non-negative values), MAX

NOT anti-monotone: AVERAGE, MIN (over negative values), VARIANCE

BUC's pruning is correct only for anti-monotone measures. For COUNT: if parent count < θ, all descendants also < θ → safely prune.

📐 H-Cubing: Top-k for Non-Anti-Monotonic Measures

H-Cubing (Hashing-based Cubing) extends BUC to handle non-anti-monotonic measures like AVERAGE by reformulating constraints.

For an AVERAGE threshold: instead of "avg ≥ θ", transform to: "sum ≥ θ × count". Both sum and count ARE anti-monotone, so their ratio can be bounded during traversal.

H-Cubing uses a heap-based structure to maintain top-k cells by average, pruning cells whose maximum possible average (given their sum and minimum count) falls below the k-th best average found so far.

This allows approximation of average-based iceberg cubes efficiently without computing every cell.

📐 BUC Complexity Analysis

Worst case (full cube, no pruning): O(2ⁿ × |D|) where |D| is database size

Best case (high sparsity, aggressive pruning): Near O(|D| × log|D|) — close to a single sort

Space complexity: O(|IcebergCube|) — only significant cells stored

In practice, on transactional databases with min_support=3 and 20+ dimensions, BUC achieves 100-1000× speedup over full cube computation.
