🛒 Basic Concepts • Card 1 of 6
🛒 The Art of Finding Hidden Patterns
🧠 Real-World Story: In the 1990s, Walmart analyzed millions of receipts and discovered something bizarre: people who buy diapers on Friday evenings also frequently buy beer! No human analyst would ever look for this connection. Data mining found it automatically.

This is Association Rule Mining — finding "If A is in the basket, then B is probably also in the basket" patterns hidden inside huge transaction databases.

The rules look like: {diapers} → {beer}. You read this as: "If someone buys diapers, they will likely also buy beer."

💡 Why does this matter? Retailers use these rules to design store layouts (put beer near diapers!), make product recommendations ("Customers also bought..."), and plan promotions. It's everywhere in modern tech.
🛒 Basic Concepts • Card 2 of 6
📦 Key Terms: Itemsets & Support

First, some vocabulary we need to understand everything else.

  • Transaction: One customer's basket. E.g., {milk, bread, eggs}.
  • Itemset: Any set of items, like {milk, bread} or {beer, diapers, chips}. A k-itemset has k items.
  • Support: What fraction of ALL baskets contain this itemset?
Support({milk, bread}) = (# baskets with BOTH milk AND bread) / (total baskets)

Example: 1000 total baskets. 200 contain both milk AND bread. So Support({milk, bread}) = 200/1000 = 0.20 = 20%.

💡 Why does support matter? Low-support rules are just coincidences. We only care about patterns that appear frequently enough to be meaningful. We set a minimum support threshold (e.g., 5%) to filter out noise.
🛒 Basic Concepts • Card 3 of 6
🎯 Confidence: How Reliable Is the Rule?

Support tells us how common an itemset is. But for a rule A → B, we also need to know: given that a basket has A, how often does it also have B?

Confidence(A → B) = Support({A, B}) / Support({A})

Concrete example:

  • 400 baskets contain milk (out of 1000)
  • 200 baskets contain BOTH milk AND bread
  • Confidence(milk → bread) = 200/400 = 0.50 = 50%

This means: "50% of the time someone buys milk, they also buy bread."

💡 Why confidence? A rule must be both common (support) AND reliable (confidence) to be useful. We mine all rules that satisfy BOTH a minimum support threshold AND a minimum confidence threshold.

🛒 Basic Concepts • Card 5 of 6
⚙️ Minimum Thresholds: Finding What Matters

Not all rules are worth our attention. We set two important filters:

  • min_support: How common must a pattern be? (e.g., appears in at least 5% of transactions)
  • min_confidence: How reliable must a rule be? (e.g., correct at least 60% of the time)

A rule A → B is only reported if it passes BOTH thresholds.

Frequent Itemset: support(X) ≥ min_support
Strong Rule: confidence(A→B) ≥ min_confidence

The mining task: Find ALL association rules from the database that satisfy both thresholds. This is harder than it sounds — there can be exponentially many candidate itemsets!

💡 The challenge: With 100 items in a store, there are 2¹⁰⁰ possible itemsets. We can't check them all. We need clever algorithms — like Apriori and FP-Tree — to do this efficiently.

⚙️ Apriori Algorithm • Card 1 of 7
🌱 The Apriori Insight: Prune First, Count Later
🧠 Analogy: Imagine you're looking for expensive restaurants with great food AND great service AND great ambience. If a restaurant doesn't have great food alone, it definitely can't have all three. You can stop investigating it immediately — no need to check the other features.

Apriori uses this same logic with itemsets:

  • If {milk, bread, eggs} is a frequent itemset, then {milk, bread}, {milk, eggs}, and {bread, eggs} must ALL be frequent too.
  • Equivalently: if {milk, bread} is infrequent, then {milk, bread, eggs} is definitely infrequent — skip it!
💡 The power: This "prune early" strategy lets us avoid checking an exponential number of candidates. Real databases have millions of transactions — without pruning, mining would be impossible.
⚙️ Apriori Algorithm • Card 2 of 7
🔬 The Anti-Monotone Property
If X is infrequent → ∀ Y ⊇ X: Y is also infrequent

This is called the anti-monotone property (or "downward closure property"). Support is anti-monotone: adding more items to a set can only decrease or maintain the support, never increase it.

Why? Every basket containing {A, B, C} also contains {A, B}. So {A, B} appears at least as often as {A, B, C}.

Think of it like a sieve: If grains of sand don't pass through a wide mesh, they definitely won't pass through a finer mesh. The anti-monotone property is the same idea applied to itemsets.
💡 Consequence: We only need to generate candidates from frequent itemsets. Any candidate with an infrequent subset gets pruned before we even count it in the database. Massive savings!

⚙️ Apriori Algorithm • Card 4 of 7
🔗 Candidate Generation: How Apriori Builds Bigger Sets

Apriori generates candidates for k-itemsets from frequent (k-1)-itemsets in two steps:

Step 1: JOIN — Take two (k-1)-itemsets that share the same first (k-2) items. Join them to create a k-itemset candidate.

Example: {A,B,C} and {A,B,D} share prefix {A,B}, so join → candidate {A,B,C,D}.

Step 2: PRUNE — Check every (k-1)-subset of the new candidate. If ANY subset is infrequent → delete the candidate immediately.

Apriori-gen(Fk-1) = JOIN step → PRUNE step → Ck candidates
💡 Efficiency: The prune step ensures we never count a candidate whose subset is infrequent — saving potentially thousands of database lookups.
⚙️ Apriori Algorithm • Card 5 of 7
📜 Rule Generation: From Itemsets to Rules

Once we have all frequent itemsets, we generate association rules from them.

For a frequent itemset L = {A, B, C, D}, we consider every possible split into antecedent and consequent:

  • {A,B,C} → {D}, {A,B,D} → {C}, {A,C,D} → {B} ...
  • {A,B} → {C,D}, {A,C} → {B,D} ...
  • {A} → {B,C,D} ...

For each candidate rule, we check if confidence ≥ min_confidence. If so, it's a strong rule!

Smart pruning: If A → BCD has low confidence, then AB → CD will have even lower confidence (or same). We can prune whole branches of the rule space using this property too!
⚙️ Apriori Algorithm • Card 6 of 7
🚀 Efficiency Improvements

Standard Apriori can still be slow. Several improvements exist:

  • Hash-based counting (DHP): Use a hash table to count 2-itemsets during the first scan, dramatically reducing C₂ candidates.
  • Transaction reduction: Remove transactions that contain no frequent k-itemsets — they can't contribute to (k+1)-itemsets.
  • Partitioning: Divide DB into partitions. Find locally frequent sets in each partition. Any globally frequent set must be locally frequent in at least one partition. Only 2 DB scans needed!
  • Sampling: Mine a random sample first to get approximate results, then verify on the full DB.
  • Dynamic itemset counting (DIC): Start counting new itemsets as soon as all their subsets are found frequent — don't wait for the next pass.
💡 Real impact: In practice, Apriori with these improvements can handle millions of transactions in reasonable time.

🌳 FP-Tree Algorithm • Card 1 of 8
🌳 FP-Tree: No Candidates Needed!
🧠 Analogy: Apriori is like searching for a book by checking every shelf in a huge library multiple times. FP-Tree is like creating a perfectly organized index of the entire library in one go, then mining the index — never touching the original shelves again!

Apriori's weaknesses:

  • Scans the database many times (once per itemset size)
  • Generates and stores huge numbers of candidate itemsets

FP-Tree's solution: Compress the entire database into a compact tree structure, then mine patterns directly from the tree. No candidate generation!

💡 Speed: FP-Tree scans the database only TWICE. In practice, FP-growth (mining an FP-Tree) can be orders of magnitude faster than Apriori on large databases.
🌳 FP-Tree Algorithm • Card 2 of 8
🏗️ FP-Tree Structure

An FP-Tree is a prefix tree (trie) with special properties:

  • Root node: empty (labeled "null")
  • Each node: stores an item name + count of how many transactions follow this path
  • Items ordered by frequency: most frequent items appear first in every transaction (so they're most likely to be shared)
  • Shared prefixes = shared nodes: if two transactions start with the same items, they share nodes in the tree — this is the compression!

Header table: A separate table that maps each frequent item to its first occurrence in the tree, with linked-list pointers to ALL other occurrences.

💡 Compression: Real databases can be compressed by 10-100x in an FP-Tree because most transactions share common prefixes (like {milk, bread} appearing in many baskets).

🌳 FP-Tree Algorithm • Card 4 of 8
🔍 Conditional Pattern Bases

Once the FP-Tree is built, how do we mine it? We process each frequent item bottom-up.

For item m: find ALL paths in the FP-Tree that end at a node labeled 'm'. These paths are called the conditional pattern base of m — they show the "context" in which m always appears.

🧠 Analogy: The conditional pattern base is like looking at everyone who bought milk and asking: "What else did they buy?" You're conditioning on milk being present.

Example: If m appears in paths {f,c,a,m:2} and {f,b,m:1}, then the conditional pattern base of m is: {{f,c,a}:2, {f,b}:1}. Notice we drop 'm' itself — it's always present!

💡 Key insight: We use the header table + node links to quickly find ALL occurrences of each item in the tree without re-scanning the database.
🌳 FP-Tree Algorithm • Card 5 of 8
🌿 Conditional FP-Trees & Recursion

After finding the conditional pattern base, we:

  1. Build a conditional FP-Tree from the conditional pattern base
  2. Mine this smaller tree recursively
  3. Each frequent pattern in the conditional tree, when combined with the current item, gives a new frequent pattern
Frequent itemsets containing m = {m} ∪ (patterns mined from conditional FP-Tree of m)

Example: If mining the conditional FP-Tree of m gives us {f}, then {f, m} is a frequent itemset!

💡 Recursion terminates when: (1) the conditional FP-Tree is empty, (2) the tree has a single path (then enumerate all subsets of the path), or (3) all items are frequent individually.

📊 Pattern Evaluation • Card 1 of 5
⚠️ The Problem with Support & Confidence
🚨 Danger Zone: A rule can have HIGH confidence and still be completely MISLEADING!

Real example from a university dataset:

  • Support(buys_video_game) = 0.60 (60% of students)
  • Support(buys_action_video) = 0.75 (75% of students)
  • Support(both) = 0.40

Confidence(game → video) = 0.40 / 0.60 = 66.7%. Sounds good!

But wait: 75% of ALL students buy videos regardless. So among game buyers, fewer buy videos (67%) than in the general population (75%). The rule is actually negatively correlated!

💡 Lesson: High confidence alone doesn't mean a rule is useful. We need better measures. Enter: Lift.
📊 Pattern Evaluation • Card 2 of 5
📐 Lift: The Better Measure
Lift(A → B) = Confidence(A → B) / Support(B) = P(A ∪ B) / (P(A) × P(B))

Lift tells us: "Does knowing A is present help predict B, or are they independent?"

Lift > 1
Positive correlation. A and B co-occur more than by chance. ✅
Lift = 1
Independent. A and B have no relationship. →
Lift < 1
Negative correlation. A actually inhibits B. ❌

For our example: Lift(game → video) = 0.67 / 0.75 = 0.89 < 1. Negative correlation confirmed!

📊 Pattern Evaluation • Card 3 of 5
🎲 The Null Transaction Problem
🧠 Analogy: Imagine you're studying the relationship between buying beer and buying diapers. In a database of 10 million transactions, maybe only 1000 involve beer and 2000 involve diapers. The other 9.997 million transactions involve neither. These are null transactions.

Measures like Lift and Chi-square are heavily influenced by null transactions. In most real databases, most items rarely co-occur, so null transactions dominate and distort results.

🚨 Example: Chi-square says beer and diapers are strongly correlated — but only because there are so many transactions with neither item!
💡 Solution: Use null-invariant measures — measures that are NOT affected by the count of transactions containing neither A nor B.
📊 Pattern Evaluation • Card 4 of 5
🎯 Kulczynski: A Null-Invariant Measure
Kulc(A, B) = ½ × (P(A|B) + P(B|A)) = ½ × (Conf(B→A) + Conf(A→B))

Kulczynski is the average of the two conditional probabilities. It asks: on average, how often does each item appear given the other?

Properties:

  • Range: [0, 1]. Higher = stronger positive association.
  • Null-invariant: Transactions containing neither A nor B don't affect the calculation at all.
  • Symmetric: Kulc(A,B) = Kulc(B,A).
Often used with: Imbalance Ratio (IR) = |P(A) - P(B)| / (P(A) + P(B) - P(A∩B)). High Kulc + Low IR = genuinely interesting rule!

1. Apriori Algorithm Pseudocode

L1 = {frequent 1-itemsets}
for k = 2; Lk-1 ≠ ∅; k++ do:
    Ck = Apriori-gen(Lk-1)       // candidate generation
    for each transaction t in DB:
        Ct = subset(Ck, t)        // get candidates in t
        for each candidate c in Ct:
            c.count++             // increment count
    Lk = {c ∈ Ck | c.count ≥ min_sup}
return ∪k Lk                      // all frequent itemsets

Apriori-gen(Lk-1):
    // JOIN step
    for p, q in Lk-1 where p[1..k-2] = q[1..k-2] and p[k-1] < q[k-1]:
        c = p ∪ {q[k-1]}          // create candidate
        // PRUNE step
        for each (k-1)-subset s of c:
            if s ∉ Lk-1: delete c; break
    return candidates

2. ECLAT: Vertical Data Format

Instead of storing transactions horizontally (transaction → list of items), ECLAT stores data vertically: item → list of transaction IDs (TID list).

Support(X) = |TID-list(X)|. Support(X ∪ Y) = |TID-list(X) ∩ TID-list(Y)| — just intersect the TID lists! No database scans needed at all.

TID-list(A) = {1,2,4,6}
TID-list(B) = {2,3,5,6}
TID-list({A,B}) = {1,2,4,6} ∩ {2,3,5,6} = {2,6}
Support({A,B}) = 2

3. Chi-Square Formula

χ² = Σ (Observed - Expected)² / Expected

For 2×2 contingency table:
Expected(AB) = (count_A × count_B) / N

χ² > threshold → reject independence
BUT: affected by null transactions!

4. Closed vs Maximal Frequent Itemsets

Maximal Frequent Itemset: A frequent itemset X such that no proper superset of X is also frequent. (Compact summary — but loses support info.)

Closed Frequent Itemset: A frequent itemset X such that no proper superset of X has the same support as X. (More information than maximal, still more compact than all frequent itemsets.)

If X is closed: ∀ Y ⊃ X, support(Y) < support(X)
Maximal ⊆ Closed ⊆ Frequent Itemsets

5. Imbalance Ratio (IR)

IR(A, B) = |P(A) - P(B)| / (P(A) + P(B) - P(A∩B))

Range: [0, 1]
IR = 0 → balanced (P(A) = P(B))
IR = 1 → maximally imbalanced

Use with Kulczynski:
  High Kulc + Low IR  → Strong, balanced association ✓
  High Kulc + High IR → Strong but imbalanced (one rare item)
  Low Kulc            → Weak or negative association
